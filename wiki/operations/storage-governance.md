# 存储架构、预算与回收

[英文入口](../../README.md) · [中文入口](../../README.zh-CN.md) · [Wiki](../README.md) · [部署与备份](../database-deployment.md)

## 数据分层

| 存储域 | 位置与职责 | 清理边界 |
| --- | --- | --- |
| 主数据库 | SQLite 或 MySQL；身份、权限、配置、凭据、目录控制状态、任务状态、持久证据引用 | 不以缓存策略删除权威记录 |
| 派生索引 | `indexes/derived.sqlite`；目录摘要、倒排词项、向量引用、日志查询、缓存元数据及治理计数 | 可重建；不能单独删除整个库来清理某一类数据 |
| 缓存正文 | `objects/cache/sha256/aa/bb/<sha256>.json` | 当前目录、历史 manifest、缓存记录等有效引用均释放后回收 |
| 持久正文 | `objects/durable/sha256/aa/bb/<sha256>.json` | 仅依据主库任务结果、审批证据等持久引用判断；缓存清理不能删除 |
| 调用日志 | `logs/calls/YYYY-MM-DD.jsonl` | 独立保留天数或显式删除 |
| 审计日志 | `logs/audit/YYYY-MM-DD.jsonl` | 独立保留天数或显式删除 |
| 目录版本指针 | `catalog/manifests/` | 当前版本及最多两个、最长 24 小时的历史版本 |
| 升级备份 | `backups/` | 保留供恢复验证，单独人工管理 |

正文按内容 SHA-256 寻址，域内去重。相同内容在缓存域和持久域各存一份，换取独立的清理边界。搜索读取摘要与索引，详情按需读取 CAS；搜索不会启动 lazy MCP，也不会批量载入全部 inputSchema。目录快照仍受实时身份、权限与版本校验约束。

旧历史目录不保留整套倒排索引；过期分页需要调用方重新搜索。当前目录仍保持精确 gateway_name、完整 inputSchema 和按原查询继续翻页的契约。

## 管理页面

管理员打开 **系统设置 → 存储治理**：

- 查看主库、派生索引、缓存/持久正文、日志、版本指针、临时文件和备份的占用；文件统计按批次扫描，未完成时明确显示进度状态。
- 设置正文、目录索引、旧索引积压、查询缓存、临时空间、并发写入、磁盘剩余空间、WAL、内存和后台回收预算。
- 执行“回收已失效数据”，触发一轮有界后台任务；仍有积压时继续由后台清理。
- 显式清除可重建查询缓存；当前已发布目录和持久任务结果继续保留。
- 迁移完成并验收后，可确认备份编号、单独删除该迁移备份；未完成迁移的备份禁止删除。任务中断会保留删除状态，可再次明确提交以续行。
- 对主 SQLite、派生 SQLite 分别配置启动压缩阈值，或手动“释放数据库空间”。MySQL 主库不显示 SQLite 压缩控件。

默认预算与行为：

| 项目 | 默认值 |
| --- | --- |
| 缓存 CAS | 4 GiB |
| 持久 CAS | 0，不额外设置总量硬限制 |
| 目录 SQL 逻辑预算 | 4 GiB |
| 待回收目录 SQL 逻辑预算 | 2 GiB |
| 临时写入 | 512 MiB、32 个槽位，所有同节点 worker 共享 |
| 持久写入预留 | 上述临时预算内预留 64 MiB、4 个槽位，缓存不能使用 |
| 磁盘剩余保护 | 至少 1 GiB 且至少磁盘容量的 10% |
| WAL 提醒 / 暂停重建 | 128 MiB / 512 MiB |
| 每类查询缓存 | 256 MiB、100000 条 |
| 向量查询缓存 TTL | 86400 秒 |
| 目录快照内存 / 正文内存 | 64 MiB / 128 MiB |
| 单轮后台清理 | 最多 2000 毫秒、50000 行 |
| 旧调用 ID 删除防护 | 最多 100000 条；可在管理页调整 |

目录 SQL 预算使用包含行、索引开销的保守逻辑估算，计数随事务回滚和级联删除变化；它与数据库实际文件大小、空闲页和 WAL 分开显示。永久日志占用不计入目录预算。达到容量上限时拒绝新增可重建内容，不静默淘汰当前已发布目录。

WAL 的文件长度可能包含已经 checkpoint 的可复用空间。暂停重建依据尚未完成 checkpoint 的帧判断，不仅根据文件长度；不强制结束读取，也不手工删除 WAL/SHM。

临时预算在文件创建前预约，随实际字节增长；失败释放预约。写入者被终止后，后台通过操作系统租约核实它已退出，只移除该预约登记的受管临时文件，不按文件名模糊删除其他数据。内存预算设为 0 可关闭对应缓存；其他容量不得低于接口校验下限。

查询缓存与当前目录向量不同：查询缓存支持容量和 TTL；当前目录向量仍按服务、owner、目录版本和模型保留，未变化内容可复用。禁用服务、发现失败和明确撤权继续遵守各自原有语义。

## 日志保留

`log_retention_days` 与 `audit_log_retention_days` 各自默认 **0=永久保存**。本次升级不擅自改变该策略，治理页面会醒目标示永久保存。

配置为 N>0 时，超过相应保留期的记录自动删除，清理原文、查询投影及无引用详情。设置为永久不意味着空间有界，应按业务保留要求配置天数，或使用日志页的显式删除功能。数据库压缩不改变日志保留规则。

新调用使用包含代际信息的 UUID 标识。物理删除和索引切换完成后，删除防护压缩为固定大小的代际元数据；其他 worker 的旧回调不能重新写入被删除记录，仍在运行的无关调用可以正常结束。旧版调用 ID 使用有界兼容删除记录；达到预算时明确拒绝进一步扩大记录，可在停服重启全部 worker 后安全回收，或由管理员提高预算。

清理按批次选择 ID，只复制受影响的日期文件，复制期间允许同节点 worker 追加日志，切换时补齐尾部并更新偏移。大文件部分清理受临时预算保护；空间不足时保留可恢复删除决定并报告失败，增加预算或释放空间后重试。所有历史正文引用均参与回收判断，无引用详情、已删除日期的源信息和已退出 worker 的租约文件分批清理。审计与调用各自使用独立连接，仍共用唯一的派生 SQLite 文件。

备份与恢复必须包含整个 `logs/`，尤其是 `calls/.sources/epochs.json`、格式标记及仍存在的删除决定。它们属于防复活控制信息；不能当作可随意删除的查询缓存。缺失或损坏时拒绝继续写入，先恢复一致的日志备份。

## API

以下接口仅管理员可用，并保留会话/CSRF 与操作时的授权校验：

| 接口 | 用途 |
| --- | --- |
| GET `/api/v1/settings/storage/governance` | 当前策略、分域文件统计、CAS 用量、SQL 估算、预约、内存和最近回收状态 |
| PATCH `/api/v1/settings/storage/governance` | 校验并保存预算；主库保存权威策略，本地派生库保存可恢复镜像 |
| POST `/api/v1/settings/storage/governance/collect` | 创建后台回收任务 |
| POST `/api/v1/settings/storage/governance/query-cache/clear` | 明确清除可重建查询缓存，后台分批执行 |
| GET `/api/v1/settings/storage/governance/backup` | 当前迁移备份是否存在及删除状态，不返回本机路径 |
| POST `/api/v1/settings/storage/governance/backup/{id}/delete` | 使用 `{"confirm":"<id>"}` 明确删除已完成迁移的对应备份 |
| GET / PATCH `/api/v1/settings/storage` | SQLite 压缩状态与独立阈值 |
| POST `/api/v1/settings/storage/{main,derived}/vacuum` | 创建后台压缩任务 |

旧 `logs` 目标别名继续映射到 `derived`，新配置和文档使用 `derived`。不得在同一次 PATCH 同时指定两个名称。

## 首次升级和恢复

首次升级先停止所有旧版本写入者。迁移在 ready 前取得目录独占权，创建并验证备份，分批核对数据后通过迁移脚本移除主库中可重建表；不保留长期双写。完成标记和 schema 必须一致，普通启动不重复复制。失败后保留阶段与源数据，再执行同一迁移命令续行。

~~~console
mmg storage status
mmg storage migrate --dry-run
mmg storage migrate
~~~

旧日志索引安全改名为 `indexes/derived.sqlite`；新调用日志写入 `logs/calls/`。历史日志仍能查询，维护不能把索引当成原文来源。升级备份、旧版无法确认归属的数据及旧任务文件不会随缓存 GC 擅自删除。

派生库丢失时，主库配置、凭据和持久结果引用不依赖缓存对象登记。缓存库存和历史 manifest 根引用恢复完成前暂停缓存对象回收；不会因为暂时查不到派生记录就删除持久正文。恢复期间不批量启动 lazy MCP。完整恢复流程见[备份与迁移](backup-and-migration.md)。

## 运行环境

Python 需要 3.12 或更高，链接的 SQLite 必须包含 WAL-reset 并发修复：**3.51.3+**，或修复分支 **3.50.7 / 3.44.6**。即使主库使用 MySQL，本地派生库也需要这一条件。未修复引擎会在打开或迁移存储前拒绝启动。依据见 [SQLite 官方 WAL-reset 说明](https://www.sqlite.org/wal.html#walresetbug)。

~~~console
uv run python -c "import sys, sqlite3; print(sys.version); print(sqlite3.sqlite_version)"
~~~

升级 uv 自身不会替换已有虚拟环境中的 Python 或 SQLite。备份并停服后，选择链接已修复 SQLite 的 Python 构建，使用原锁文件重建应用环境；不要只检查 Python 主次版本号。仓库 Dockerfile 单独构建并校验固定版本 SQLite，仅为 Python 的 SQLite 扩展设置私有库路径，生产层不包含编译器，也不向下游 MCP 注入全局动态库环境变量。容器部署仍应在实际构建的镜像内检查版本。

派生 SQLite 使用同主机文件锁与 WAL，不应放到网络共享目录供不同节点共同写入。存储层支持同节点多连接/worker 的预约、发布与回收互斥；当前网关下游运行时仍由一个实例拥有，同目录不能启动多个独立网关运行时。未来多节点需要独立的运行时协调和共享持久对象方案，不能仅共享一个 MySQL 主库就视为完成多节点部署。
