# 渐进式发现

## 为什么不直接暴露全部工具

传统聚合方式会在 Agent 初始化时返回所有下游工具定义。MCP 数量增加后，会同时带来：

- 初始化等待多个服务；
- 大量 Schema 占用上下文；
- 模型需要在过多工具之间选择；
- 不常用进程也可能被提前启动；
- 配置和授权变化要求客户端重新载入。

MMG 的 discovery 模式将发现分成两级，并把执行保持为第三步。

## 两级发现

### 第一级：服务摘要

`gateway_search_mcps` 搜索服务名称、slug、描述和标签。空查询或 `*` 列出当前 Token 可访问的服务摘要。

摘要只包含做下一步选择所需的信息，不返回连接配置、环境变量或认证材料。

### 第二级：完整工具定义

`gateway_search_tools` 在指定服务或全部授权服务中搜索工具。每个结果包含：

- 精确 `gateway_name`；
- 原始工具名和服务归属；
- 完整 description；
- 完整 `inputSchema`；
- 存在时的 `outputSchema`、annotations 和元数据；
- 调用包装说明；
- 可靠示例或明确标记的参数模板。

Schema 不会简化为字段列表。`required`、嵌套结构、enum、default、`additionalProperties`、`anyOf`、`oneOf`、`$defs` 和 `$ref` 都应保留。

### 第三级：精确调用

`gateway_call` 只接受发现结果中的精确名称：

~~~json
{
  "name": "example__echo",
  "arguments": {
    "value": "hello"
  }
}
~~~

执行入口不使用模糊搜索或向量模型选路。它重新检查授权、参数、配置版本和运行时状态。

## 搜索不会启动服务

目录来自能力缓存。查询服务、搜索工具和分页不会启动 `lazy` 下游。只有 `gateway_call`、资源读取或明确的管理操作才可能取得运行实例。

缓存缺失、过期或发现失败必须作为可诊断状态返回，不能伪装成“服务没有工具”。

## 分页与一致性

全量查询表示“可以遍历完整目录”，不是一次返回无限数据。

- 使用返回的 `next_cursor`；
- 翻页时保持查询条件不变；
- 工具定义不会跨页拆分；
- 目录或权限变化会使旧游标失效，客户端应重新查询；
- 稳定排序避免重复和遗漏。

## 精确、关键词与向量

默认检索优先级：

1. 精确服务 ID、slug 或完整网关名；
2. 精确工具名；
3. 前缀和子串；
4. 名称、描述和参数文本的关键词相关度。

可以配置 OpenAI 兼容 embedding 接口做语义重排。向量检索：

- 默认关闭；
- 只重排已经通过授权过滤的候选；
- 不替代精确匹配；
- 不参与最终执行路由；
- 服务不可用时回退关键词；
- 不发送连接凭据或实际调用参数。

## native 模式

native 模式直接返回权限范围内的原生工具目录，适合工具较少或客户端要求原生注册的情况。它与 discovery 模式共享授权、缓存和调用运行时，只是披露方式不同。
